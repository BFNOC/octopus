### 2. Critical Issues (必须修改)
#### 🔄 站点同步合并逻辑覆盖已禁用状态 
- **位置**: [internal/sitesync/storage.go:L292-339](file:///Users/chaos/developments/github_go/octopus/internal/sitesync/storage.go#L292-L339) (`mergeReadyIncomingSiteToken`)
- **分析**: 
  在 `SiteTokenEnabledForProjectedChannelKey` 中，系统成功将数据库中的 `SiteToken` 的 `enabled` 状态更新为了 `false`。然而，当后台 `sitesync` 定时任务（或用户手动触发同步）运行时，`mergeReadyIncomingSiteToken` 会被调用来合并从上游同步过来的新令牌。
  在合并逻辑中，匹配到本地已有的 `existing` Token 时：
  ```go
  incoming.ID = existing.ID
  incomingsToken := strings.TrimSpace(incoming.Token)
  existingToken := strings.TrimSpace(existing.Token)
  if existingToken != "" && existingToken != incomingsToken {
      incoming.Token = existingToken
  }
  if existing.ID != 0 {
      usedExistingIDs[existing.ID] = struct{}{}
  }
  return incoming
  ```
  此时 `incoming` 的 `Enabled` 默认值通常为 `true`。这里并没有像 `mergeMaskedIncomingSiteToken`（第 360 行、391 行）那样保留已有令牌的禁用状态：
  ```go
  incoming.Enabled = incoming.Enabled && existing.Enabled
  ```
  这就导致下一次同步周期到来后，数据库中的 `SiteToken` 将被重置为 `Enabled = true`。进而由于 `sitesync.ProjectAccount` 的自动投影，本地已被禁用的 `ChannelKey` 会被重新激活，使得自动禁用机制彻底失效。
- **修复建议**: 
  在 [internal/sitesync/storage.go:L315](file:///Users/chaos/developments/github_go/octopus/internal/sitesync/storage.go#L315) 之前，加入状态继承逻辑：
  ```go
  incoming.Enabled = incoming.Enabled && existing.Enabled
  ```
  同样，在第 336 行返回前也应确保继承该状态。

### 3. Warnings (建议修改)
#### ⚠️ "billing" 匹配词过宽，存在误判风险
- **位置**: 
  - [internal/health/classifier.go:L46](file:///Users/chaos/developments/github_go/octopus/internal/health/classifier.go#L46) (`hardSignals`)
  - [internal/relay/degrade.go:L30](file:///Users/chaos/developments/github_go/octopus/internal/relay/degrade.go#L30) (`forbiddenBlockSignals`)
- **分析**:
  直接使用字符串 `billing` 作为硬失败及直接降级的特征词风险很高。任何包含该子串的临时性报错（例如 `"failed to fetch billing status due to network timeout"` 或 `"billing system temporary unavailable"`）都会被直接归类为 `FailureHard`（硬失败），从而导致通道被直接隔离（Quarantined）或降级，造成误判。
  实际上，在 [internal/upstreamerr/quota.go:L29](file:///Users/chaos/developments/github_go/octopus/internal/upstreamerr/quota.go#L29) 中，新引入的 `ClassifyQuotaExhaustion` 已经做出了安全且合理的二级匹配：只有当包含 `"billing"` 且同时包含 `"hard limit"`、`"quota"`、`"额度"`、`"余额"` 之一时，才会识别为余额耗尽。
- **修复建议**:
  建议在 `hardSignals` 和 `forbiddenBlockSignals` 中移除单纯的 `"billing"` 关键字，完全交由更加精准的 `upstreamerr.IsQuotaExhaustion(normalized)` 逻辑处理。

### 5. Info (其他反馈与重构建议)
#### 💡 并发缓存更新与异步 DB 写入的一致性风险
- **位置**: [internal/op/quota_disable.go:L17-26](file:///Users/chaos/developments/github_go/octopus/internal/op/quota_disable.go#L17-L26) (`ChannelKeyEnabled`)
- **分析**:
  `ChannelKeyEnabled` 是直接调用数据库的 `Update` 将 `enabled` 写入 DB，然后再手动同步更新了本地的 `channelCache` 和 `channelKeyCache`。
  然而，在 [internal/op/channel.go:L126](file:///Users/chaos/developments/github_go/octopus/internal/op/channel.go#L126) 中，系统原有一套利用 `channelKeyCacheNeedUpdate` 队列进行批量异步保存的逻辑 `ChannelKeySaveDB`。
  如果同一时间该 Key 在其他协程中被触发了属性变更（如统计指标、余额扣减），旧的 Key 实体可能已经被放入了 `channelKeyCacheNeedUpdate` 中等待写入。此时 `ChannelKeyEnabled` 绕过队列直接更新 DB，随后的 `ChannelKeySaveDB` 批量回写时可能携带旧的状态，导致 DB 状态被意外回写覆盖。
- **建议**:
  可以考虑在直接修改 DB 时，加锁并从 `channelKeyCacheNeedUpdate` 队列中移除对应的 ID，或者在 `ChannelKeyEnabled` 执行时同步刷新并发控制状态。

#### 💡 细化 forbiddenExclusions
- **位置**: [internal/relay/degrade.go:L41](file:///Users/chaos/developments/github_go/octopus/internal/relay/degrade.go#L41)
- **分析**:
  不同模型服务商在模型不支持或上下文超长时的错误用词不尽相同。例如 Anthropic Claude 可能会返回 `"model_not_supported"`，有的可能返回 `"max_tokens"` 限制。
- **建议**:
  在 `forbiddenExclusions` 中额外补充 `"model_not_supported"`、`"max_tokens"`、`"token limit"` 等字样，以防这些用户端输入错误在 403/400 状态码下意外触发通道降级。
