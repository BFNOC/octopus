## Analysis: 余额不足错误自动禁用策略

### 结论

#### 1. 错误识别缺口

上游返回的 `insufficient_user_quota` 错误 **不会被识别为 quota/billing 硬失败**。原因是三个匹配层全部遗漏：

| 匹配层 | 文件 | 匹配模式 | 能否命中 `insufficient_user_quota` |

| WS 配额 | `internal/relay/ws_error.go:168-172` | `insufficient_quota` | **不能** — 同上 |

额外遗漏的信号：
- `new_api_error` — 三处均未匹配
- `预扣费额度失败` / `余额不足` — 无中文匹配
- 该错误体不含 `billing` 子串，所以 `billing` 信号也兜不住

**唯一能兜住的情况**：如果上游 HTTP 状态码返回 `403`，则 `DegradeMap` (`degrade.go:14`) 和 `ClassifyFailure` (`classifier.go:53`) 的状态码路径会将其归类为 `forbidden` / `FailureHard`。但如果上游返回 `400` 或其他非标准状态码，则完全漏过。

#### 2. 站点-渠道-账号绑定关系

```
Site ──1:N── SiteAccount ──1:N── SiteChannelBinding ──1:1── Channel ──1:N── ChannelKey
```

- 投影逻辑 — `internal/sitesync/project.go:20`：`ProjectAccount()` 从 SiteAccount 生成 Channel + ChannelKey

即 SiteAccount 禁用后，投影会自动禁用其所有 managed channel。

#### 3. 最小安全禁用粒度

| 粒度 | 效果 | 适用场景 | 推荐度 |
|------|------|----------|--------|
| **ChannelKey** | 仅禁用该令牌，其他 key 仍可用 | 单个 token 额度耗尽 | ★★★ 最小爆炸半径 |
| **SiteAccount** | 禁用账号 → 投影禁用所有绑定 channel | 账号级余额耗尽 | ★★★★ 最佳平衡 |
| Channel | 禁用该协议通道 | 该账号某协议耗尽但其他协议正常 | ★★ 适用面窄 |
| SiteModel | 禁用单个模型 | 模型级定价差异大 | ★ 颗粒太细，不解决根本 |
| Site | 禁用整个站点 | 过于激进 | ★ 不推荐 |

**推荐**：以 **SiteAccount** 为主粒度。余额不足是账号级问题，同账号下所有 channel/key 都会受影响。配合 ChannelKey 级别的软降级作为第一道防线。

**避免误禁的过滤条件**：

| 错误类型 | 状态码 | 文本特征 | 应禁用？ |

### 风险

1. **风险：误禁** — 如果上游误报余额不足（临时 bug），整个 SiteAccount 被禁用会导致服务中断
   → **缓解**：仅在连续 N 次（建议 3 次）余额不足错误后才触发禁用，而非单次

2. **风险：循环依赖** — `relay` 包引入 `op` 包可能导致循环引用
   → **缓解**：通过 interface 或 callback 注入禁用逻辑，或抽取独立的 `quota` 包

3. **风险：并发竞态** — 多个请求同时触发禁用，重复写 DB 和投影
   → **缓解**：使用 `sync.Map` 或 singleflight 做 per-account 去重，幂等写入

4. **风险：禁用后无恢复路径** — 用户不知道账号被禁用，余额充值后仍无法使用
   → **缓解**：前端显示禁用原因；定期 sync 余额自动恢复；提供手动 re-enable 入口

5. **风险：上游状态码不一致** — 不同平台对余额不足返回不同状态码（400/403/200+error body）
   → **缓解**：以文本匹配为主、状态码为辅的双重判定策略
