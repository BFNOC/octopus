```go
// DisableChannelKeyAndSiteToken 自动禁用指定 ChannelKey 及其托管源的 SiteToken
func DisableChannelKeyAndSiteToken(channelID, keyID int, ctx context.Context) error {
	// 1. 获取并禁用本地 ChannelKey，更新内存缓存及落库
	var key model.ChannelKey
	if err := db.GetDB().WithContext(ctx).First(&key, keyID).Error; err != nil {
		return err
	}
	key.Enabled = false
	if err := db.GetDB().WithContext(ctx).Model(&key).Update("enabled", false).Error; err != nil {
		return err
	}
	ChannelKeyUpdate(key) // 更新本地缓存

	// 2. 如果是投影托管渠道，查询绑定并禁用对应的源 SiteToken
	binding, managed, err := ChannelManagedBinding(channelID, ctx)
	if err == nil && managed {
		var token model.SiteToken
		if err := db.GetDB().WithContext(ctx).
			Where("site_account_id = ? AND group_key = ? AND token = ?", 
				binding.SiteAccountID, binding.GroupKey, key.ChannelKey).
			First(&token).Error; err == nil {
			token.Enabled = false
			db.GetDB().WithContext(ctx).Model(&token).Update("enabled", false)
		}
	}
	return nil
}
```

### 三、 风险与避坑指南

1. **上游同步覆盖风险**：
   如果仅在 `relay.go` 链路中修改 `ChannelKey.Enabled = false`，那么一旦后台触发了 `sitesync` 定时任务（或用户手动触发“站点同步”），同步逻辑会将上游的 Token 数据重新合并入库，本地禁用状态将**彻底失效**。请务必按照“实现建议”中第三步的方式，在 `mergeReadyIncomingSiteToken` 中增加禁用合并继承规则。
2. **上下文过长等误禁风险**：
   上游模型在遭遇 `"context_length_exceeded"` 时也可能返回 `400` 甚至其他非标准 Status Code。在执行自动禁用时，必须确保绝对被 `forbiddenExclusions`（模型不支持、上下文超限）所拦截，仅在精准命中诸如 `quota` / `billing` / `invalid_api_key` / `banned` / `401` 时才执行 Key 的硬禁用。
3. **轮询空转风险**：
   若同一个 `Channel`（对应站点特定的 `GroupKey`）下的所有 Keys 共享同一额度池，当额度耗尽时，第一个 Key 失败并自动禁用，负载均衡器会自动轮询第二个 Key 再次触发失败并禁用，直至该 Channel 下的 Keys 全部被禁。这符合安全断电原则。由于 Keys 被永久置为 `Enabled = false`，后续请求将直接在迭代器初始化时在 [internal/relay/relay.go:107](file:///Users/chaos/developments/github_go/octopus/internal/relay/relay.go#L107) 抛出 `no available channel`，从而彻底截断向站点的无效轮询，消除封号隐患。

#### 2. 在业务逻辑层实现精准禁用函数
在 [internal/op/channel.go](file:///Users/chaos/developments/github_go/octopus/internal/op/channel.go) 中添加禁用工具函数。此函数同时更新本地 `ChannelKey` 和投影源的 `SiteToken`：
```go
// DisableChannelKeyAndSiteToken 自动禁用指定 ChannelKey 及其托管源的 SiteToken
func DisableChannelKeyAndSiteToken(channelID, keyID int, ctx context.Context) error {
	// 1. 获取并禁用本地 ChannelKey，更新内存缓存及落库
	var key model.ChannelKey
	if err := db.GetDB().WithContext(ctx).First(&key, keyID).Error; err != nil {
		return err
	}
	key.Enabled = false
	if err := db.GetDB().WithContext(ctx).Model(&key).Update("enabled", false).Error; err != nil {
		return err
	}
	ChannelKeyUpdate(key) // 更新本地缓存

	// 2. 如果是投影托管渠道，查询绑定并禁用对应的源 SiteToken
	binding, managed, err := ChannelManagedBinding(channelID, ctx)
	if err == nil && managed {
		var token model.SiteToken
		if err := db.GetDB().WithContext(ctx).
			Where("site_account_id = ? AND group_key = ? AND token = ?", 
				binding.SiteAccountID, binding.GroupKey, key.ChannelKey).
			First(&token).Error; err == nil {
			token.Enabled = false
			db.GetDB().WithContext(ctx).Model(&token).Update("enabled", false)
		}
	}
	return nil
}
```

### 三、 风险与避坑指南

1. **上游同步覆盖风险**：
   如果仅在 `relay.go` 链路中修改 `ChannelKey.Enabled = false`，那么一旦后台触发了 `sitesync` 定时任务（或用户手动触发“站点同步”），同步逻辑会将上游的 Token 数据重新合并入库，本地禁用状态将**彻底失效**。请务必按照“实现建议”中第三步的方式，在 `mergeReadyIncomingSiteToken` 中增加禁用合并继承规则。
2. **上下文过长等误禁风险**：
   上游模型在遭遇 `"context_length_exceeded"` 时也可能返回 `400` 甚至其他非标准 Status Code。在执行自动禁用时，必须确保绝对被 `forbiddenExclusions`（模型不支持、上下文超限）所拦截，仅在精准命中诸如 `quota` / `billing` / `invalid_api_key` / `banned` / `401` 时才执行 Key 的硬禁用。
3. **轮询空转风险**：
   若同一个 `Channel`（对应站点特定的 `GroupKey`）下的所有 Keys 共享同一额度池，当额度耗尽时，第一个 Key 失败并自动禁用，负载均衡器会自动轮询第二个 Key 再次触发失败并禁用，直至该 Channel 下的 Keys 全部被禁。这符合安全断电原则。由于 Keys 被永久置为 `Enabled = false`，后续请求将直接在迭代器初始化时在 [internal/relay/relay.go:107](file:///Users/chaos/developments/github_go/octopus/internal/relay/relay.go#L107) 抛出 `no available channel`，从而彻底截断向站点的无效轮询，消除封号隐患。
